# KylinBootLab 设计方案

- 日期：2026-07-15
- 状态：已由参赛者批准
- 对应赛题：第四题 openKylin 操作系统启动性能分析与优化
- 项目定位：冲刺最高奖项的全链路启动性能分析、优化与验证系统

## 1. 目标

KylinBootLab 的目标不是提供一组针对单台机器的调优命令，而是建立一套能够测量、解释、优化、验证并迁移 Linux 客户端启动性能的方法与工程系统。

系统以 openKylin 为主平台，覆盖 Linux 内核、initramfs、systemd、显示管理器和 UKUI 用户会话，形成从内核启动到桌面真实可用的统一时间轴。系统通过因果图、资源模型、离散事件模拟和自动化 A/B 实验寻找有效优化，并由 BootAgent 辅助根因分析和实验设计。所有最终结论必须由确定性工具和裸机实验验证。

## 2. 设计原则

- 用户可用性优先：进程启动或 unit active 不等于界面可交互。
- 证据优先：任何优化都必须对应可追溯事件、依赖、源码或实验结果。
- 功能不回退：不得通过关闭必要能力或把工作推迟到首次使用来换取启动数字。
- 可回滚：每项修改都必须有前置检查、验证条件和恢复路径。
- 可迁移：核心分析与实验框架不得绑定 openKylin、UKUI 或 14700K。
- AI 受约束：Agent 可以提出假设和实验，但不能绕过安全检查直接修改系统。
- 原始数据不可变：报告中的每个数字都能追溯到运行、镜像、配置和补丁版本。

## 3. 范围

### 3.1 范围内

- 内核启动、initramfs、udev、systemd、显示管理器和 UKUI 会话分析。
- 登录界面就绪、桌面 UI 就绪和桌面真实可用的语义化探测。
- systemd 依赖、服务激活、CPU/I/O 资源、关键文件访问和桌面组件优化。
- openKylin/UKUI 源码级补丁、配置级优化及其上游化材料。
- 裸机冷启动自动编排、统计实验、功能回归和故障恢复。
- Ubuntu 裸机与 Fedora 虚拟机上的迁移验证。
- 基于本地模型或可替换模型后端的 BootAgent。

### 3.2 范围外

- BIOS、UEFI 自检、固件和 GRUB 菜单等待时间优化。
- 依赖 NVIDIA 独立显卡或其他专有硬件的方案。
- 未经验证的 Agent 自动提权和任意 root 命令执行。
- 关闭图形登录、移除必要功能或制造明显首用卡顿的优化。
- 只对 14700K 有效且没有普通 x86 回退路径的核心功能。

## 4. 目标环境

KylinBootLab 使用双机闭环架构。

| 角色 | 硬件 | 职责 |
|---|---|---|
| 控制机 | RTX 3060 Laptop | 实验编排、数据分析、报告生成、本地模型推理 |
| 被测机 | Intel Core i7-14700K、UHD 770、独立 SSD | openKylin 裸机启动、性能采集、优化执行、功能验证 |

控制机与被测机优先通过有线网络连接。被测机启用 Wake-on-LAN 和可用的硬件 watchdog。独立 SSD 划分实验系统和恢复环境；正式实验只测量实验系统，恢复环境不进入性能结果。

主实验使用开始阶段可获得的最新 openKylin 官方稳定标准镜像，并在第一次正式基线前冻结 ISO 校验值、软件源快照、内核和软件包版本。之后不得在同一组 A/B 实验中滚动更新。网络功能探针只访问控制机提供的固定测试端点，不依赖公网延迟或可用性。

## 5. 成功标准

项目以覆盖全部评分项为目标，性能目标是登录界面和桌面可用时间改善至少 30%，冲刺 40% 以上。该数值是优化目标，不替代统计显著性和功能正确性。

- 基线和优化版本分别完成不少于 30 次正式冷启动。
- 报告中位数、P95、方差、效应量和 95% 置信区间。
- 优化版本连续完成 100 次冷启动并到达可用桌面。
- 登录、网络、音频、输入法、文件管理器、终端和设置中心回归全部通过。
- 正式 benchmark 模式对启动时间的中位数测量开销低于 1%。
- 至少形成三项相互独立、收益显著、能够回滚的优化。
- 形成 openKylin、UKUI、systemd 或内核方向的可上游补丁及提交材料。
- 核心分析器无需修改即可处理 Ubuntu 和 Fedora 适配器产生的数据。
- BootAgent 相比通用 LLM 直接读日志，在已知根因基准集上具有更高命中率和更低危险建议率。

## 6. 总体架构

```text
控制机 KylinBootLab Controller
  实验编排器 ─ 数据仓库 ─ 因果分析器 ─ 优化规划器
       │                         │
       └──── WOL / SSH ──────────┘
                    │
被测机 openKylin Target
  早期启动采集器 → systemd采集器 → 登录探针 → 桌面可用探针
        │               │              │
        └──────── 统一事件流 ───────────┘
                    │
          事务式优化执行与自动回滚
```

### 6.1 实验编排器

实验编排器管理冷启动、实验顺序、配置切换、运行超时和数据回收。每次运行生成唯一 `run_id`，并绑定 `boot_id`、系统镜像哈希、软件包清单、内核版本、优化方案、环境状态和实验模式。

接口：接收声明式 `ExperimentManifest`，输出运行状态与不可变运行目录。

依赖：Wake-on-LAN、SSH、目标机 agent 和数据仓库。

### 6.2 目标机采集器

目标机采集器覆盖内核 tracepoint、initcall、调度、块 I/O、文件访问、systemd transaction、journal、显示管理器和 UKUI 会话事件。所有事件映射到 `CLOCK_BOOTTIME` 纳秒时间轴。

采集器提供两种模式：

- `diagnostic`：启用 ftrace、eBPF、调度和 I/O 等高细节事件，用于定位根因。
- `benchmark`：仅保留低开销时间标记和状态探针，用于正式性能比较。

eBPF 后端优先使用 libbpf CO-RE；缺少 BTF 或相关内核能力时自动切换到 ftrace/perf 后端。

接口：输出版本化 `Event` 记录，不负责解释或修改系统。

### 6.3 就绪状态探针

就绪探针负责把内部启动状态映射为用户可感知状态。

登录界面就绪必须同时满足：greeter 已渲染、键盘输入能够响应、显示管理器健康、D-Bus 和 NetworkManager 工作正常。系统通过专用测试账号和 `uinput` 发起真实登录，不使用 autologin。

桌面可用必须同时满足：UKUI 桌面、面板和托盘出现，启动器能够响应，终端哨兵应用出现首帧，网络、音频设备和输入法接口可用。其他常用应用紧随其后执行功能回归，避免同时启动多个程序污染主指标。

接口：输出版本化 `ReadinessEvent` 和失败原因，不参与关键路径推断。

### 6.4 因果分析器

因果分析器将 unit、进程、内核事件、资源等待和就绪事件构造成有向图。图中的边分为 systemd 顺序依赖、运行时阻塞、CPU/I/O 竞争和用户可用性门控。systemd 已解决的循环按 transaction 结果处理；运行数据中的强连通分量在分析前折叠。

分析器计算：

- 指向 `Tlogin-ready` 与 `Tusable` 的最长关键路径。
- 节点 slack、独占耗时和跨运行关键路径出现概率。
- 调度等待、I/O 等待和依赖等待的收益上限。
- 基线与优化运行之间的结构和时序差异。

接口：读取不可变事件和系统元数据，输出 `CausalGraph`、瓶颈证据及预测模型输入。

### 6.5 离散事件模拟器

模拟器使用实测服务时长、依赖关系、CPU 拓扑和 I/O 容量，预测缩短节点、删除无效边、改变资源权重或预取关键文件后的启动时间。模拟结果只用于排列候选实验优先级，不能代替裸机 A/B 验证。

### 6.6 优化规划器与执行器

规划器按以下原则排序候选：

```text
候选得分 = 预期收益 × 证据置信度 × 可迁移性
           ÷ 稳定性风险 ÷ 验证成本
```

每个 `OptimizationPlan` 必须包含前置条件、证据引用、具体改动、预期指标、证伪条件、功能验证和回滚步骤。执行器仅处理通过 schema 和安全策略的方案，并以 profile、systemd generator、版本化软件包或独立内核/initramfs 启动项实施改动。

### 6.7 验证器

验证器负责性能 A/B、功能回归、首用性能、连续启动、故障注入和跨发行版测试。它是所有优化和 Agent 建议的最终门控，不满足标准的候选不会进入最终补丁集。

### 6.8 BootAgent

BootAgent 通过结构化工具访问因果图、运行数据、模拟器、源码检索和实验系统。它不直接访问无限制 root shell，也不能自行绕过人工审批和验证器。

BootAgent 由四个顺序角色组成：

- `Trace Analyst`：定位异常路径和跨运行波动。
- `Source Investigator`：检索 openKylin、UKUI、systemd、内核源码和文档，提供可核查引用。
- `Experiment Designer`：把假设转换为最小 A/B 实验和证伪条件。
- `Safety Critic`：检查功能回退、首用延迟、硬件过拟合和恢复能力。

默认模型固定为 Qwen2.5-Coder-7B-Instruct GGUF Q4_K_M，通过 llama.cpp 运行，使用 8192 token 上下文和确定性解码；显存不足的层由 CPU/RAM 承担。模型接口保持可替换，但正式对比结果必须使用固定模型、量化文件校验值和推理参数。RAG 语料包含官方文档、源码、unit 文件、历史运行和已验证案例。Agent 输出必须符合 JSON Schema，并引用具体证据。

## 7. 数据模型与数据流

核心数据对象如下：

| 对象 | 内容 |
|---|---|
| `RunManifest` | 运行、镜像、内核、软件包、配置、硬件和环境信息 |
| `Event` | 时间戳、来源、事件类型、主体、资源及关联字段 |
| `ReadinessEvent` | 就绪状态、通过的探针和失败原因 |
| `CausalGraph` | 节点、边、权重、证据、slack 和关键性概率 |
| `OptimizationPlan` | 改动、证据、风险、预期收益、验证和回滚 |
| `ValidationResult` | 性能统计、功能结果、失败分类和是否接纳 |

原始事件保存为压缩、只追加的 JSONL；运行清单、指标、图索引和验证结果保存到 SQLite。HTML 报告从原始事件和 SQLite 重新生成。任何中断运行均保留并标记 `invalid`，不得静默删除。

完整数据流为：

1. 控制机选择实验 profile 并安排下一次一次性启动。
2. 被测机进入 S5，控制机等待稳定窗口后发送 Wake-on-LAN。
3. 目标机从内核早期开始记录事件，随后运行登录和桌面探针。
4. 运行成功后，目标机上传数据、环境清单和校验值。
5. 因果引擎生成关键路径，模拟器估算候选收益。
6. BootAgent 或规则系统提出最小实验计划。
7. 人工批准后，执行器应用事务式 profile 并重复 A/B 实验。
8. 验证器决定接受、拒绝或隔离该候选。

## 8. 测量定义

统一时间点如下：

| 时间点 | 定义 |
|---|---|
| `T0` | Linux 内核单调启动时钟的零点，通过内核事件和 `CLOCK_BOOTTIME` 对齐，不含 BIOS、UEFI 和 GRUB 等待 |
| `Tkernel` | PID 1/systemd 开始运行 |
| `Tlogin-ui` | 图形登录界面完成渲染 |
| `Tlogin-ready` | 登录界面输入和基础服务探针通过 |
| `Tsession` | 用户会话开始 |
| `Tdesktop-ui` | UKUI 核心桌面组件完成 |
| `Tusable` | 桌面交互、哨兵应用和常用能力探针通过 |

主指标为 `Tlogin-ready - T0`、`Tusable - T0`、`Tusable - Tsession`、关键路径长度和常用应用首帧时间。辅助指标包括 CPU/IO 等待、并行度、unit 激活时长、运行波动和桌面空闲资源占用。

## 9. 实验协议

正式实验执行以下固定协议：

1. 固定 BIOS、内核、软件包、网络、CPU 策略和测试账号。
2. 记录 CPU 温度、SSD 状态、软件包清单和配置哈希。
3. 系统进入 S5 并等待固定稳定窗口，再由控制机唤醒。
4. 环境安装或大规模配置切换后的前几轮作为预热数据，不进入正式统计。
5. 基线与优化采用随机化 ABBA 分块顺序，各完成不少于 30 次。
6. 使用配对分析、bootstrap 置信区间和效应量判断收益。
7. 同时报告中位数、P95、方差和失败次数，不只报告平均值。
8. diagnostic 与 benchmark 数据分开；正式成绩只使用 benchmark 模式。

候选优化进入最终补丁集必须满足以下硬门槛：主指标中位数改善至少 2%，且 bootstrap 95% 置信区间下界高于零；或者某个关键阶段同时改善至少 100 ms 和 1%，且置信区间下界高于零。主指标 P95 相对基线不得回退超过 1%；常用应用首用时间的 95% 置信区间上界不得超过基线 5%，其中位数绝对增量不得超过 100 ms。功能回归必须全部通过，并具备自动回滚路径。

## 10. 四层优化设计

### 10.1 内核与 initramfs

- 根据真实硬件建立启动所需驱动闭包，减少无效模块和固件探测。
- 比较压缩算法、镜像大小、解压 CPU 时间和存储读取之间的权衡。
- 定位 initcall、udev、块设备和设备超时的关键路径。
- 对能够证明独立且安全的设备初始化进行并行化或异步化。
- 保留兼容硬件清单和通用回退镜像，避免生成只能在单机启动的镜像。

### 10.2 systemd

- 删除没有真实因果意义的顺序边，但不删除必要功能依赖。
- 将适合的常驻服务改为 socket、D-Bus 或 path 激活。
- 并行化独立服务，修复不合理超时、重试和设备等待。
- 根据关键性设置启动阶段 CPU/IO 权重。
- 通过 drop-in 或可上游 unit 补丁交付，不直接修改 vendor 文件。

### 10.3 资源调度与关键预取

- 识别 CPU 型、I/O 型和阻塞型关键节点。
- 在 14700K 上把关键 CPU 工作放到 P 核，把非关键后台工作放到 E 核。
- 通过 cgroup v2 和 systemd 资源控制实现，普通 x86 上自动退化为通用权重策略。
- 从多轮文件访问轨迹学习稳定的关键文件集合。
- 在根文件系统和会话阶段使用 io_uring 合并预读，并在 I/O 压力升高时主动停止。

### 10.4 显示管理器与 UKUI

- 定位同步 D-Bus 调用、串行插件加载、配置扫描和小文件访问。
- 将彼此独立的初始化并行化，修复阻塞主线程的调用。
- 为关键组件增加明确 readiness 信号。
- 优化可安全缓存的数据，并为缓存建立准确失效机制。
- 非关键工作只能在功能和首用性能测试证明无回退时后移。

## 11. 核心创新

### 11.1 语义化概率关键路径

把用户可用状态、系统依赖和资源竞争放入同一因果图，并统计每个瓶颈跨多轮启动成为关键节点的概率。该方法比单次 systemd 甘特图更能识别稳定瓶颈和随机抖动。

### 11.2 拓扑与资源感知的启动规划

联合考虑依赖、P/E 核、CPU/IO 权重和关键文件预取，通过模拟器寻找组合优化，避免多个局部优化相互抵消。

### 11.3 可验证的 Agent 实验闭环

Agent 负责观察、检索、提出假设和设计实验；确定性工具负责安全检查、执行、统计验证和回滚。系统通过已知故障基准集证明 Agent 的实际增益，而不是只展示对话效果。

## 12. BootAgent 评测

故障基准集包含服务超时、错误设备等待、DNS/网络等待、I/O 竞争、错误依赖、模块探测、桌面插件阻塞和后台任务资源争抢等可逆场景。每个案例具有已知根因、证据位置和预期修复方向。

评测比较三种方法：

- systemd 等传统工具的原始输出。
- 通用 LLM 直接读取日志。
- BootAgent 调用因果图、源码检索和模拟工具。

评测指标为 Top-K 根因命中率、有效建议率、危险建议率、收益预测误差和人工分析时间。所有模型版本、量化方式、提示、知识库清单和工具输出均固化到实验清单中。

## 13. 安全、恢复与错误处理

恢复环境是 GRUB 默认入口，实验系统通过 `grub-reboot` 作为一次性入口启动。成功到达 `Tusable` 后，目标机才为下一轮重新安排实验入口；若启动失败或 watchdog 重启，一次性入口已被消费，系统自动进入恢复环境。

配置级优化通过 profile 和 systemd generator 产生运行时 drop-in。源码级优化使用版本化软件包，并在实验根分区上自动切换基线与优化版本。恢复环境能够挂载实验根分区、恢复软件包和配置、提取日志。正式 A/B 实验始终在同一实验根分区上执行，并在切换 profile 后重建约定缓存，减少分区布局差异。

错误分类如下：

- 启动失败：保存 pstore、前一轮 journal 和内核日志，恢复基线。
- 登录失败：保存显示管理器状态、截图、窗口树和 D-Bus 快照。
- 桌面失败：记录缺失组件、会话日志和探针结果，判定功能回归。
- 性能回退：保留完整数据并拒绝候选，不与其他优化组合。
- Agent 异常：schema、证据或安全策略不通过时拒绝执行。
- 网络或传输中断：目标机本地持久化数据，恢复连接后按校验值续传。

对内核启动早于 watchdog 生效的极端失败，恢复流程允许控制机判定超时后要求人工硬复位；该运行标记为失败并保留。系统不声称能够软件恢复尚未启动内核的机器。

## 14. 测试策略

| 测试类型 | 规模 | 通过标准 |
|---|---:|---|
| 单元与属性测试 | 每次变更 | 数据解析、图算法、schema、统计和 profile 逻辑通过 |
| 测量开销校准 | 基线与采集模式各 30 次 | benchmark 中位数开销低于 1% |
| 性能 A/B | 每个候选各不少于 30 次 | 达到候选硬门槛，主指标 P95 回退不超过 1% |
| 功能回归 | 每个候选 | 登录、网络、音频、输入法和常用应用全部通过 |
| 首用性能 | 每轮正式启动 | 95% 置信区间上界不超过基线 5%，中位数绝对增量不超过 100 ms |
| 连续冷启动 | 最终优化版 100 次 | 100% 到达可用桌面 |
| 故障恢复 | 不少于 20 个故障场景 | watchdog 生效后的故障一次自动重启进入恢复环境；更早故障被控制机检测并可人工复位恢复 |
| Agent 基准 | 不少于 30 个已知根因案例 | 完整报告命中率、危险建议率和时间节省 |
| 跨发行版 | Ubuntu 裸机、Fedora 虚拟机 | 核心分析器不修改即可处理适配数据 |

桌面自动化使用 AT-SPI、D-Bus、`uinput` 和截图校验。除核心 UI 外，测试文件管理器、终端、设置中心、浏览器、软件包管理、登录/注销和关机重启，并记录桌面空闲后的 CPU、内存和磁盘活动。

## 15. 跨发行版设计

差异封装为 `distro adapter`、`desktop adapter` 和 `initramfs adapter`。核心事件 schema、因果图、模拟器、实验编排、Agent 工具和统计报告不包含发行版分支。

- openKylin 裸机完成全部分析、优化和稳定性验证。
- Ubuntu LTS 在同一 14700K 机器上轮换安装，验证 systemd、资源调度和关键预取的裸机迁移。
- Fedora Workstation 虚拟机验证不同 initramfs、软件包体系和桌面环境适配。

跨发行版结果不要求复现相同百分比，但必须证明核心方法可运行、瓶颈解释正确，并至少验证一项通用优化的正收益。

## 17. 实施阶段与门槛

| 阶段 | 主要工作 | 完成门槛 |
|---|---|---|
| 0. 实验台 | openKylin、恢复环境、WOL、watchdog、固定环境 | 自动完成冷启动并可靠回收结果 |
| 1. 基线 | 30 次以上完整冷启动 | 指标稳定，波动来源可解释 |
| 2. 可观测 | 统一事件流与 readiness 探针 | benchmark 开销低于 1%，事件可追溯 |
| 3. 因果引擎 | DAG、关键路径、资源模型、模拟器 | 正确诊断一批人工注入瓶颈 |
| 4. 主体优化 | systemd 与 UKUI 源码优化 | 三项独立、显著、可回滚收益 |
| 5. 深度优化 | initramfs、P/E 核、关键预取 | 组合收益冲刺 30% 至 40%，无首用回退 |
| 6. BootAgent | 工具调用、源码 RAG、实验闭环 | 相比通用 LLM 提升诊断准确率与安全性 |
| 7. 泛化 | Ubuntu 裸机、Fedora 虚拟机 | 核心分析器无需修改即可运行 |
| 8. 决赛固化 | 100 次启动、报告、演示、上游材料 | 数据可复算，现场演示可恢复 |

阶段按完成门槛推进，不按固定日历时间推进。BootAgent 在确定性分析工具稳定后接入，避免模型替代尚未建立的测量和因果能力。

## 19. 主要风险与缓解措施

| 风险 | 缓解措施 |
|---|---|
| 30% 性能目标无法达到 | 优先优化 systemd 与 UKUI 真实关键路径；如绝对收益较低，以严谨方法、上游补丁和泛化成果补足 |
| 全量 trace 扰动启动 | diagnostic 与 benchmark 分离，并单独测量观察开销 |
| UKUI 自动化接口不稳定 | 组合 AT-SPI、D-Bus、窗口树、截图和 uinput，保存多源证据 |
| P/E 核方案过拟合 14700K | 将拓扑策略封装为插件，在普通 x86 上使用通用权重回退 |
| 关键预取争抢 I/O | 使用关键性阈值和压力反馈，收益不显著时自动停用 |
| Agent 幻觉或危险建议 | 强制结构化输出、证据引用、安全检查、人工批准和实验验证 |
| 源码补丁未及时上游合并 | 提交高质量补丁、测试和复现材料；以提交记录而非合并状态作为项目交付 |
| 优化导致无法启动 | 一次性 GRUB 入口、watchdog、恢复环境和事务式 profile |
| 冷启动数据波动大 | 固定环境、记录温度与 SSD 状态、随机化 ABBA 分块和足量重复 |

## 20. 已确认决策

- 目标是最高得分上限，不以个人经验、团队人数或固定周期限制方案范围。
- 采用全栈旗舰路线，不选择纯手工调优、纯内核极限优化或纯 AI 展示。
- 使用双机裸机实验架构，14700K 主机使用独立 SSD 安装 openKylin。
- 确定性因果引擎是核心，BootAgent 是受验证器约束的创新模块。
- 覆盖内核/initramfs、systemd、资源调度和显示/UKUI 四层优化。
- 正式结果必须包含统计实验、功能回归、故障恢复和跨发行版验证。
